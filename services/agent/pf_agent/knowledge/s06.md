# ⑥UXデザイン担当の知識の束

UX の専門家として PdM と相談するときの土台。名前を出した原則・手法は広く知られたもの。数字は出典の確かなものだけを書き、
条件つきのものは条件も書いている。ここにないことは、自分の専門知識で補う（不確かなら「未確認」と言う）。

## ゼロから磨き上げる順番
1. **目的と成功の基準を決める**：誰の、どの行動が、どう変われば成功か。事業の指標（④⑤）と体験の指標をつなぐ。
   体験の指標は HEART（Google の Kerry Rodden らの枠組み：Happiness・Engagement・Adoption・Retention・Task success）
   から選び、Goals → Signals → Metrics の順で具体化する。
2. **対象者を知る**：仮説のペルソナ（proto-persona）から始め、インタビューで確かめて直す。
3. **課題を言い切る**：ジャーニーの中で、最も痛い瞬間（感情が落ちる段階）を特定する。「どうすれば〜できるか（HMW）」の
   問いにする。
4. **広げてから絞る**：解き方の案を複数出し（Double Diamond の発散→収束。英国 Design Council）、評価の軸を先に決めて選ぶ。
5. **流れと構造**：ユーザーフロー（正常・例外・空の状態）→ 画面一覧と情報設計（IA）。
6. **触れる形にする**：プロトタイプ（⑥の UI）で、主要なタスクを通しで試せるようにする。
7. **確かめて直す**：ユーザビリティテスト → 直す → また試す。受入基準とユーザビリティ基準に落とす。
- 各段で「何を決めたか・なぜか」を合意メモに残し、前の段の根拠がないまま次の段を決めない。

## 対象者を知る（リサーチ）
- **インタビュー**：未来の仮定（「使いますか？」）ではなく、過去の具体的な出来事（「最後に〜したのはいつ？ そのとき何を
  した？」）を聞く。Rob Fitzpatrick の *The Mom Test* の考え方：褒め言葉・仮定の約束は証拠にならない。
- **Jobs to Be Done**：人は製品を「雇って」片付けたい用事（job）がある。状況（When…）・動機（I want to…）・
  期待する結果（So I can…）で書く。機能ではなく、置き換えている代替手段（Excel・紙・家族に頼む など）を見る。
- **文脈の観察（Contextual Inquiry）**：実際に作業している場で、手順・道具・回避策（workaround）を見る。回避策は機会の印。
- **日記調査**：頻度の低い・長い期間にわたる体験（月末の締め・引っ越し など）に向く。
- **定量と定性**：定量は「何が・どれだけ」、定性は「なぜ」。片方だけで結論を出さない。
- **何人に聞くか**：ユーザビリティテストの「5人で問題の大半が見つかる」（Nielsen と Landauer の研究）は、同じ利用者層・
  同じタスクで、繰り返し試す前提の話。利用者層が違えば層ごとに必要。インタビューは、新しい発見が出なくなる（飽和）まで。

## 整理する（統合）
- **親和図**：観察した事実を付箋1枚1事実にして、似たものを下から束ねる（上から分類を決めない）。
- **ペルソナ**：属性より、目的・行動・困りごと・使う場面で書く。調査の裏づけのないペルソナは「仮説」と明記する。
  1つのプロダクトで主に設計する相手（primary）は1人に絞る（Alan Cooper の考え方）。
- **カスタマージャーニー**：段階ごとに行動・接点・考え・感情・機会。感情の谷が最優先の機会になりやすい。
- **ストーリーマップ**（Jeff Patton）：横に行動の流れ、縦に優先度。最初のリリースは、流れを端から端まで通る最小の帯にする。

## 課題の言い方と優先度
- **HMW（How Might We）**：広すぎず狭すぎない問いにする（「家計簿を良くする」は広い、「ボタンを大きく」は狭い）。
- **Kano モデル**（狩野紀昭）：当たり前品質（ないと不満）・一元的品質（あるほど満足）・魅力的品質（あると喜ぶ）。
  MVP は当たり前品質を外さず、魅力的品質を1つだけ尖らせる。
- **影響×確からしさ×手間**で並べる（RICE や ICE などの点数づけは、比べるための道具で、正しさの保証ではない）。

## 構造（情報設計）
- **カードソート**：利用者に分類させ、利用者の頭の中の分け方（メンタルモデル）を知る。オープン（名前も付けさせる）と
  クローズド（決めた分類に入れる）。
- **ツリーテスト**：画面なしで、階層だけで目的のものを見つけられるかを試す。
- **ナビゲーション**：主要な行き先は 3〜5 個に絞る。スマホでは下のタブバー、深い階層より検索・最近使ったもの。
- **ラベル**：社内の言葉ではなく、利用者の言葉で。

## 操作の原則
- **Nielsen の10のユーザビリティ原則（ヒューリスティクス）**：システムの状態を見せる／現実の言葉と合わせる／
  利用者が主導できる（取り消し・やり直し）／一貫性と標準／エラーを防ぐ／覚えさせず見て選ばせる／柔軟さと効率（慣れた人の
  近道）／美しく最小限／エラーを理解し回復できる／ヘルプと説明。画面を見直すときの観点として使う。
- **Don Norman**（*The Design of Everyday Things*）：アフォーダンスとシグニファイア（何ができるかが見て分かる）・
  フィードバック（押したら結果が返る）・マッピング（操作と結果の対応が自然）・制約（間違った操作をできなくする）・
  概念モデル（利用者が仕組みを正しく想像できる）。
- **Fitts の法則**：遠く小さい的ほど押しにくい。主要な操作は大きく、指の届く所に（スマホは画面下）。
- **Hick の法則**：選択肢が増えるほど決めるのに時間がかかる。一度に見せる選択肢を絞り、段階的に見せる。
- **段階的な開示**：最初は必要なものだけ、詳しい設定は後ろに。
- **ゲシュタルト**：近いもの・似たもの・囲まれたものは仲間に見える。余白と揃えで構造を伝える。
- **Shneiderman の8つの黄金律**：一貫性・慣れた人の近道・有益なフィードバック・区切りのある対話・エラー処理・
  取り消し・利用者が主導・短期記憶の負担を減らす。

## 体験の質
- **最初の価値までの時間（time to value）**：登録・設定を後回しにし、最初の数分で「役に立つ」を体験させる。
  オンボーディングは説明より、実際にやって見せる。
- **空の状態**：何もないときに、次にすることと、できた時の姿を見せる。
- **フォーム**：項目を減らす・1列に並べる・ラベルは入力欄の上・入力しながら確かめる・エラーは項目のそばに直し方を書く。
- **待ち時間**：0.1秒以内なら即時、1秒を超えたら進んでいることを、10秒を超えたら進み具合と中断を見せる（Nielsen の
  応答時間の目安）。
- **文言（UX ライティング）**：動詞で始めるボタン、結果が分かる言葉、責めないエラー文。
- **感情のデザイン**（Norman の3つの層）：見た目の第一印象（本能）・使いやすさ（行動）・意味や自己像（内省）。
- **習慣と動機**：BJ Fogg の行動モデル（行動＝動機×能力×きっかけ）。能力を上げる（簡単にする）方が、動機を上げるより
  効きやすい。
- **ダークパターンを使わない**：解約を隠す・既定でオンの同意・偽の希少性・罪悪感をあおる文言など。短期の数字は上がっても
  信頼を失い、規制の対象にもなりうる。

## アクセシビリティ
- WCAG 2.2 の4原則：知覚できる・操作できる・理解できる・堅牢。
- 文字と背景のコントラストは、通常の文字で 4.5:1 以上（AA）。色だけで情報を伝えない。
- タップできる大きさを十分に取る（WCAG 2.2 の最小は 24×24 CSS px。押しやすさの目安としては 44pt 前後が多く使われる）。
- キーボードだけで操作できる・読み上げで意味が通る（ボタンに名前・画像に代替テキスト）。

## 確かめる（評価）
- **ユーザビリティテスト**：タスクを渡して、考えていることを声に出してもらう（思考発話）。誘導しない。見るのは成功率・
  かかった時間・つまずいた所・その理由。
- **SUS（System Usability Scale）**：10問の質問票。平均はおよそ 68（Jeff Sauro らの集計）。比べる道具として使う。
- **ヒューリスティック評価**：専門家が原則に照らして問題を挙げる。安く早いが、利用者のテストの代わりにはならない。
- **A/B テスト**：十分な量があるときの、1つの変更の効果の確かめ。量が少ない段階では、定性のテストの方が学びが多い。

## よくある失敗
- 調べる前に画面を描き始める（解き方から入って、課題を外す）。
- 平均的な「みんな」に向けて作る（誰にも刺さらない）。
- 機能を足して解決しようとする（減らす・順番を変えるで解けることが多い）。
- 正常な流れだけを設計する（エラー・取り消し・空の状態・通信が切れたとき を忘れる）。
- 社内の言葉・組織図のままの画面構成。
- テストで説明しすぎる・誘導する（本当のつまずきが見えない）。
- 数字の目標がない（良くなったかを判断できない）。

## 相談で最初に聞くとよい問い（例）
- このプロダクトで、最初に一番うれしくなってほしい人は誰で、その人のどの瞬間を変えたいか。
- その人は、いま何で代わりに済ませているか（そのやり方の何が不満か）。
- 最初のリリースで、通しでできるようにしたい1つのタスクは何か。
- 成功したと言えるのは、何がどれだけ変わったときか。
- 使う場面（場所・時間・機器・急いでいるか）はどうか。
