# Product Factory (MVP / R0)

1人の Product Builder が、アイデアから運用まで 14 ステージ（P1〜P5、ゲート G1〜G4）を 1 つの Web アプリ上で回すための工場。
AWS Labs の AI-DLC を拡張し、Google ADK 2.x の Workflow で各ステージを動かす。設計は [docs/design.md](docs/design.md)。

## 構成

```
apps/web          Next.js 16 + Auth.js v5（テナントとロールはセッションからだけ渡す）
services/agent    FastAPI + Google ADK 2.13（ステージ実行・工場DB・監査ログ）
infra/nginx       リバースプロキシ（外に出すのは web だけ）
infra/terraform   gcp（Cloud Run の土台：Artifact Registry / Secret Manager / サービスアカウント / Workload Identity）
.github/workflows ci / infra / deploy / ide
ide               Code-OSS の Web 版（ソースからビルド）と、リポジトリを読む拡張機能
```

設計からの差分（R0 時点）

- ステージの順序とゲートは工場エンジン（決定的なコード）が持ち、各ステージの中身（質問→生成→自己監査→承認）を ADK の Workflow が 1 ステージ実行 = 1 セッションで動かす。人の入力待ち（RequestInput）は DB に残り、プロセスを再起動しても再開できる（テストで確認済み）。
- web の DB アクセスは Prisma ではなく `pg` + `apps/web/db/schema.sql`。テーブルは Tenant / User / TenantMember の3つ。Prisma のエンジン取得が開発環境から遮断されたためで、テーブルが 3 つだけなのでこのまま進める。
- 工程の順序でロックしない。どのステージからでも始められ、最新版が変わると参照している下流が「要再確認」になる。フェーズ末の審査（G1〜G4）は進行のロックではなく判断の記録。
- プロダクトごとに、ステージを使うか（開閉）と、更新に承認を求めるかを設定できる。承認の既定は個人モードがなし、法人モードがあり。
- 成果物は文章ではなく項目ごとの値（下書き）で持つ。P1〜P2 はフレームワーク（①リーンキャンバス、②TAM/SAM/SOM、③競合比較とポジショニング、④バリュープロポジションキャンバス、⑤KPIツリー・PL）、⑦は業務一覧（業務領域→業務→作業の階層と種類）とスイムレーン型の業務フロー（フローエディタ）・業務ルール・役割・例外。⑥UXデザインはペルソナ・カスタマージャーニー（ペルソナ×段階の地図。行動・接点・感情・体験の課題と機会）・ストーリーマップ（US-xx）・ユーザーフロー（UF-xx。分岐・例外つき）・受入基準（AC-xx）・画面一覧と情報設計（上位の画面・主な情報と操作）・ユーザビリティ基準、⑧は機能要求（FR-xx、ストーリーIDで⑥とつなぐ）・非機能要求（IPA 非機能要求グレードの6分類と水準）・外部接続、⑬は⑥の受入基準を取り込んだ網羅表とテストケース。ID は空なら自動で振り、⑥→⑧、⑥→⑬ の網羅を画面に出す。⑨はコンポーネント（CP-xx）・概念データモデル（ER図：エンティティ・属性の PK/FK・多重度つきリレーション）・処理仕様（PR-xx：処理区分・起動・概要・主な処理・入出力とテーブルの CRUD・リクエスト/レスポンスのパラメータ・呼び出す部品のクラスとメソッド・設定値）・状態遷移（対象ごとの状態と、イベント・条件・処理つきの遷移）・API契約・ユニット分割。CRUD マトリクス（作る処理・読む処理のないテーブルを知らせる）と、処理ごと・全体のデータフロー図は処理仕様から自動で描き、マトリクスのマスを押すとその処理の入出力に反映する。⑩は構成図（リソースを置き場所のゾーンごとに並べて通信でつなぐ）・リソース・環境・通信要件・IaC方針・月額コスト（合計を自動計算）、⑪は運用方針・運用スケジュール・起動停止・監視項目（分類別）・SLO・障害対応（重大度別）・バックアップとリカバリ（RPO/RTO）・バッチ・ログ・セキュリティ運用・CI/CD・AI評価。図はドラッグで配置を整えられ、Markdown では Mermaid（erDiagram・stateDiagram・flowchart）と表になる。以前の見出しだけの下書きは設計方針に引き継ぐ。⑫⑭は見出しごとの文書。更新すると版になり、Markdown にして下流と監査に渡す。
- 各ステージの右側でAIと対話する。AIは項目ごとの書き換え案を出し、人が採用したものだけが下書きに入る。対話の1往復は ADK の Workflow（発言と案を作る → 案を項目の型で検査して保存）で動く。
- 概要ページの上部（プロダクト名・進み具合の下）に「プロダクト・キャンバス」を置く。①リーンキャンバスと④バリュープロポジションの値（最新版を優先、なければ下書き）から画像生成AIでプロダクトの全体像（利用シーン／画面イメージ／コンセプト／グラレコ）を描き、表紙として同じテナントの人と共有する。画像は使ったプロンプトと一緒に工場DBに残す。モデルは `PF_IMAGE_MODEL`（既定 `gemini-3.1-flash-image`）、APIキーがなければ仮のSVG。既定は「自由に描く」で、書いた指示をそのまま画像モデルに渡す（画風や条件を足さない。プロダクトの内容は参考として添えるかを選べる）。できた絵は「直す」で、その絵を元に指示どおり描き直せる（新しい1枚として残り、元の絵をたどれる）。型として、利用シーン・画面・コンセプト（画風を決めてあり絵の中に文字を描かせない）とグラレコ（顧客・課題・独自の価値提案・ソリューションを日本語の見出しと短い言葉で手描き風に描かせる）もある。追加の指示は、決めてある画風や条件より優先する。
- ⑤のKPIツリーはグラフで編集する（KPIを選んで子を足す、点をドラッグして親子をつなぎ替える、分解の式 × / + を決める）。値は表と同じ行（KPI・親KPI・分解の式・目標値・計測方法）で持つので、AIの案もそのまま使える。
- サイドバーはボタンか `[` キーで隠す・表示する。右側のパネル（AIタブ・参照タブ）は `]` キーかタブで開閉する。どちらも状態は cookie に残す。
- AIタブの対話はセッションに分けられる（新しく始める・切り替える・名前を変える）。各セッションは ADK のセッションと1対1。「レポート」でステージの全セッションを要約・決まったこと・却下した案・未決事項にまとめる。
- 参照タブでは、事業フェーズ（①〜⑤）の成果物（最新版、なければ下書き）をその場で読める。
- 文書タブは編集できる。「## 項目名」の見出しごとにキャンバスの項目へ反映する（フローなど文書から読めない項目は変えない）。
- 「確定」ではなく「更新」と呼ぶ。下書きを更新すると版が1つ増え、その版が最新版になる。
- スケジュール（`/p/{id}/schedule`）：エージェントが定期的に動く予定を、cron を書かずに選ぶ（◯分ごと・◯時間ごと・毎日・平日・曜日を選ぶ。詳しい設定として cron も書ける）。選ぶたびに読み方（「毎週月・水曜 9:30」）と次の3回を出し、10分より短い間隔には注意を出す。PM・領域ごとの担当・会議をまとめて選んで同じ予定にする・止める・動かす。これから24時間の時間割（エージェント×1時間ごとの回数）と、すべてのプロダクトの予定（グループごとの予定・止めている数・次の時刻）を並べる。プラットフォームの見回りの間隔（1・5・10・15・30・60分、テナントごと）もここで変える。エージェントの組織の画面の設定も同じ選び方。毎分の呼び出し（Cloud Scheduler）は固定。
- ペルソナ・スキル・ツール（テナントで共通の配役。画面は `/p/{id}/cast`、変えられるのは管理者）：エージェントごとにペルソナ（役割名・性格・大事にすること・話し方・得意・気をつけること。⑥の担当は UX デザイナー）と、直結するスキル・使ってよいツールを割り当てる。スキルは2種類：エージェントに直結するスキル（その役割の手順と判断の基準）と、参照スキル（共通の知識を小さく分けたもの。直結するスキルが参照したときだけ読み込む。深さ3・12個・2.4万文字まで、同じものは1回）。1つのスキルは8000文字までで、長くなるものは参照スキルに分ける。固定のロジックはツール（`tools.py`）にし、スキルが名前で呼ぶ：読むツール（工程の下書き・項目の定義・上流の確定版・取り込んだ資料を読む／探す・Issue・掲示板・網羅の計算・CRUD マトリクス・ファクトリーの稼働状況）は AI が必要なときに呼ぶ（1回の実行で6回まで。スキルの prefetch に書いたものは AI を呼ぶ前に読む）。書くツール（項目への書き込み・Issue の更新と起票・掲示板・PM の記録・修正の提案）は AI が最後の出力に入れ、コードが型・宛先・権限を検証してから実行する。使えるツールは「割り当てたツール ∩ 読み込んだスキルが使うと書いたもの ∩ 役割で使えるもの」で、スキルが使うのに割り当てていないツールは警告に出る。標準のスキル（`services/agent/pf_agent/skills/*.md`）はリポジトリで管理し、テナントは画面でスキルを作る・標準を上書きする（消すと標準に戻る）。参照が輪になるスキルは作れない。ジョブの記録には、使ったスキルと読んだツールが残る。
- エージェントの組織：PdM（人）と、事業 PM（①〜⑤）・設計 PM（⑥〜⑪）・実装 PM（⑫〜⑭）、①〜⑭の担当。PdM が話せるのは PM だけで、担当とは直接話さない（工程の画面の右は「この領域の PM と話す」。担当には PM が Issue で伝える）。各担当も PdM に直接話しかけず、自分の領域の PM に上げる。PM は1時間ごとに領域の担当へ状況確認を出し（掲示板の「定時の状況確認」スレッド。領域の担当は全員が今の状況を返事し、変わっていない担当は「前回から変化なし」と添える。最後に PM が返事の数と変化のあった担当をまとめる）、集めたことを PM のタスク管理の場所（PM の作業場所）に残す。AI を呼ぶのは変化か PM 宛ての Issue があるときだけ。各工程の担当は10分ごとに自分宛てで終わっていない Issue を確かめ、あれば実行計画を立てて実行し、工程の下書きに書き込み（変えた項目は Issue の記録と監査ログに残る）、状態・進捗率を更新して起票した人か確認が要るエージェントに返す。なければ AI は使わない。承認者の修正指示（Request Changes）は、その領域の PM から担当への Issue になる。
- Issue（#n。Redmine と同じ形）：トラッカー・状態（新規・進行中・解決・フィードバック・終了・却下）・優先度・担当・起票者・開始日・期日・進捗率・親、更新ごとの記録（注記と属性の変更前後）。宛先は PM と各工程の担当まで（PdM は宛先にできない）。PdM が起票・書き込みできるのは PM 宛ての Issue だけ。起票・付け替え・書き足しをすると担当にすぐリクエストが飛ぶ（担当は10分ごとの確認でも拾う）。
- 掲示板：プロダクトの進み具合について、他のエージェントに確認が要ることを伝え合う場所（確認・回答・共有。エージェント同士だけで、PdM は読むだけ）。動く必要があることは Issue で管理する。
- 振り返りの会議（1日1回。既定は平日 18:00）：時刻になると各 PM が前回からの担当の実行状況・起きた課題・Issue の動きをレポートにまとめ、他の PM のレポートと自分の領域の成果物（今の下書き）を突き合わせて食い違いを探す。PdM は会議の画面でレポートと突き合わせを読み、PM と話す（決めたことは PM が Issue にする）。
- 定期実行は必ず動かす：Cloud Scheduler が毎分 `/internal/scheduler/tick` を呼ぶ。時刻が過ぎた予定は次の呼び出しで1回動き、起動に失敗したら時刻を戻してやり直す。画面を開いていないプロダクトにもエージェントを置く。AI の呼び出しには上限時間（10分）と再試行を付け、時間を過ぎても終わらないジョブは失敗にして理由を残す。最後に呼ばれた時刻と各担当が最後に確かめた時刻を画面に出す（ダッシュボード・エージェントの組織）。
- ダッシュボード（プロダクトのトップ）：組織と工程のグラフ（PM を領域の真上に置き、担当ごとの健全度・進み具合・報告・自分宛ての Issue・各案。工程のつながり、指揮系統、この7日の掲示板と Issue のやり取りを線で）と、案ごとのグラフ。PM との対話・今日の振り返りの会議・対応が必要な工程・定期実行の状態を並べる。
- プラットフォームエージェント：ファクトリー全体（テナントのすべてのプロダクト）が動いているかを見張り、PdM と直接話す（PM・担当とは別の存在。プロダクトの中身ではなく処理系を見る）。AI を使わず記録から決まった規則で問題を見つける（定期実行から5分ごと・画面を開いたとき）：定期実行（tick）が来ていない・止まっている、ジョブが始まらない、ジョブの失敗（種類・プロダクト・原因ごと。最後に成功してからの回数。LLM の利用上限・認証の失敗は重く扱う）、担当が拾っていない Issue（担当は30分・PM は2時間が目安）、やり取りが往復し続ける Issue、期日を過ぎた・3日以上動いていない Issue、予定の時刻を過ぎても動いていない・次の予定がないエージェント、止めているのに Issue を抱えたエージェント、詰まっていると報告している担当。同じ問題は1件にまとめ、見つからなくなったら自動で解決にする。重い問題が新しく出たら PdM に「【要対応】」で知らせる。対処は「承認して実行」したものだけ動く（定期実行を1回動かす・担当を動かす・予定を立て直す・止めたエージェントを再開する）。対話では稼働状況と問題を材料に答え、運用の対処と処理系（コード）の修正案を出す（コードは自分では直さない）。画面は `/p/{id}/platform`（稼働状況・問題・プロダクトごとのエージェントの実行状況・ジョブ・対話）、⌘K の「@プラットフォーム」でも話せる。
- ナビゲーション（エージェント時代）：左のレールはページではなく「人」を並べる。いちばん上にプラットフォーム（未対応の稼働の問題の数）、続いて3人の PM と各工程の担当が顔と状態（作業中＝回る輪・PdM の返事待ち＝脈打つ・止まっている＝赤・閉じている＝薄く）・未読・報告の一言で並び、押すとその担当の部屋（工程の画面と対話）に入る。工程グループ（事業・要求設計・構築・リリース）は色で分ける。レールは5秒ごとに状態を読み直し（画面を開いている間だけ。どのページでも）、「状態の更新 時:分:秒」と定期実行が最後に来た時刻を出す（読めないとき・定期実行が5分以上来ていないときは赤）。道具（掲示板・資料・報告資料・ジョブ・議論・設定など）と振り返りはレールの下にアイコンでまとめる。⌘K（どこからでも）で行き先を言葉で探すか、そのまま PM に話しかける（「@⑨ 状態遷移に取消を足して」は⑨の領域の設計 PM に「⑨について」話す。PM はその場で答え、要れば担当に Issue を起票する）。読み違えないよう、行き先も相手も候補として見せ、選んだものだけを実行する。
- エージェントの顔：3人の PM と各工程の担当を、同じ画風のイラストにする（画像生成AI。テナントで共通の配役、エージェントの組織の「顔を描く」でジョブ avatars）。描いていない担当や描けない環境では、役割から決まる幾何学模様の顔を出す。顔はレール・ダッシュボードのグラフ・掲示板・Issue・PM との対話に出る。
- 対話への添付：PM との対話に、資料（Excel・Word・PowerPoint・テキスト）や画像をクリップ・ドロップ・貼り付けで添えられる（1回5個まで）。添えたものはその発言のときだけ AI が読み（資料は文章にして、画像はそのまま。画像を読める接続のとき）、工程の値や取り込んだ資料にはならない。履歴には名前だけ残る。
- 資料の取り込み：手元の Excel・Word・PowerPoint（.xlsx .docx .pptx）やテキストを上げると、中身を文章にし（Excel はセルと図形の文字、Word は見出しと表、PowerPoint はスライドごと）、ジョブ（import）が「どの工程のどの項目にあたるか見分ける → 工程ごとに項目の値を抜き出す → 入れる」を行う。入れ方は「AI の案として出す」（各工程の対話に「資料の取り込み：ファイル名」のセッションで案が並び、採用したものだけ入る）か「空の項目には直接入れる」（値がある項目は上書きせず案にする）。資料に書かれていないことは入れない。割り当て先の工程は絞れる。取り込みが終わると、割り当てた工程の担当に掲示板で知らせ、担当は動くときと PdM と話すときに、資料のうち自分の工程の項目名・工程名がよく出てくる章を読む（PM は資料の一覧と割り当て先・冒頭を読む）。資料ごとに「読んでいいエージェント」を割り当てられる（既定は割り当てた工程の担当と、その領域の PM。全員・誰にも読ませない、も選べる）。
- 報告資料（RP-n）：各工程の企画情報から範囲（工程→項目。まとめ選びあり）を選び、題・読み手・目的・枚数を決めると、ジョブ（report）が「集める→構成と本文を作る→表を付録にする」を行う。本文は1枚1メッセージで根拠の工程を持ち、表・処理仕様（CRUD マトリクス）・ER・構成図は付録の表にそのまま付ける（12行で分ける）。使う中身は最新版（なければ下書き）か下書き。画面でスライドを直し・並べ替え・足し引きして、PowerPoint（ノート付き）と Markdown に書き出す。
- 自律エージェント（AG-n）：cron（分 時 日 月 曜日、日本時間。よく使う形はボタン）で仕事を予定する。仕事は「工程の見直し」（選んだ工程を上流の最新版と突き合わせ、食い違い・必須の抜け・根拠のない数値・古い前提を探す）・「自由な指示」・「リサーチライブラリの更新」・「報告資料の作り直し」。見直しと指示はジョブ（agent：工程を読む→見直す→受け箱に出す）で動き、見つけたことは受け箱に提案（重大度・根拠・項目の直し案）として届き、予定を作った人に通知する。提案は「採用して入れる（案を選べる）・確認済み・却下」にするか、返信して AI と詰める（AI が答え、必要なら案を直す）。AI が工程の値を直接書き換えることはない。時刻の判定は `/internal/scheduler/tick`：Cloud Run では Cloud Scheduler（pf-agent-tick、毎分、pf-web の SA の ID トークン）が呼び、手元では `PF_SCHEDULER=thread` でプロセスの中で1分ごとに回す。次の時刻を書き換えられた方だけが動かすので、二重には動かない。「今すぐ」でいつでも動かせる。
- 各ステージの「以降の工程を自動開発する」：上流（押したステージまでの最新版、なければ下書き）に従って、AI が違いのはっきりしたパターン（案）を決め、案ごとに後工程（⑪運用方式設計まで）の下書きと、ブラウザで触れる単一ファイルの試作を作る。できたものはプリプロダクト（PP-n）として残り、並べて比べ、試作を触り、1つを採用すると各ステージの下書きに入る（人がそこから直して更新・承認する）。試作は sandbox の iframe で、通信なしで動かす。作ったあとで上流の版が変わると知らせる。各ステージの画面の上部に「本線／PP-n 案…」のタブが出て、案ごとのそのステージの下書きを本線と同じ見た目で読める。工程ごとに「この工程だけ本線に取り込む」で案を選び分けられる。採用した案を実コードにして Cloud Run に展開するのは次の段。
- ジョブ：自動開発のような時間のかかる処理は、Cloud Run Jobs（`pf-autodev`。agent と同じイメージで入口だけ `python -m pf_agent.worker <job_id>`）で動かす。手元・テストでは裏のスレッド。右上の「ジョブ」（プロダクトのサイドバーからも）で、ジョブの定義・実行中の一覧・グリッド（実行 × 工程の状態、Airflow のグリッドにあたる）・実行履歴・使った LLM のトークン量（モデル別）を見て、取り消し・作り直しができる。ジョブの中は依存関係つきの工程（自動開発：パターンを決める → 案ごとの後工程 → 試作、リサーチ：検索・RSS → 記事を読む → 論点のまとめ）に分けて記録し、ジョブの画面で工程のグラフ・ガント・一覧（状態・時刻・所要・工程ごとのトークン・失敗の理由）を見られる。自動開発を始めると、このジョブの画面に移る。
- 新しいプロダクトは、トップの「新しいプロダクトをつくる」から AI の聞き取りで作る。AI が1〜2問ずつ聞き、分かったこと（名前・作るもの・誰のためか・困りごと・解決のしかた・選ばれる理由・MVP か PoC か）を右にまとめる。人が右で書き換えた項目は AI が上書きしない。作ると、答えた内容が①リーンキャンバスの下書きに入り、続けてプロダクト・キャンバスの最初の1枚（表紙）をジョブ（`canvas`）で裏で描く。聞き取りの途中は保存しない。
- 社内のオントロジー（右上の網の目のアイコン）：社内の用語・組織・役割・業務プロセス・システムと、その関係（〜の一種・〜の一部・〜が担当・〜を使う・〜の前に行う・関係する）をテナントで1つ持つ。一覧とグラフで編集し、決定記録・ドキュメントから AI が用語の候補を出す（人が承認したものだけが使われる）。AI は、扱う文章（ステージの対話・自動開発の上流・会話からの抜き出し）に名前か別名が出てくる概念と、その周り1段の関係だけを前提として受け取る。何が渡るかは画面で確かめられる。書き出し・読み込みは SKOS（W3C の語彙の標準）の Turtle と JSON-LD（rdflib）。
- リサーチライブラリ（右上の本棚のアイコン）：トピックごと（RL-n）の資料室。タブは「ニュース・論点・技術調査・業界調査・公的データ・プレーヤー・ファクトDB・データ分析」。
  - 集める：「更新」はジョブ（`research`）で、前回の最新記事より後の記事を AI の検索・RSS / Atom・指定したページから集める（1回60件まで、公開アドレスだけ。転送先も確かめる）。AI の検索は、接続が Claude（Anthropic API・Vertex AI）なら Claude をエージェントとして動かし、期間を最大12に区切って、区切りごとに Web 検索（Vertex AI は `web_search_20250305`、Anthropic API は `web_search_20260209`。1回8検索まで）を繰り返させ、見つけた記事を伝えて「まだ見つけていない記事」を探し直す（新しく3件未満になったら次の区切りへ）。Gemini の接続でも同じく、期間を最大12に区切って区切りごとに Google 検索グラウンディングを最大3回まで探し直させ（1件1行で書かせ、出典の対応から URL・見出し・日付を取る）、論点・企業の切り口でも1回ずつ探す。記事への質問と調査レポートの下調べも同じ接続の Web 検索を使う。本文を開けない記事は検索結果の文章から作り「本文未確認」にする。期間の始まりを決めていれば毎回そこから探す（URL で重ねない）。手で URL か本文を足すこともできる。記事（RA-n）ごとに日本語の見出し・要約・国・区分・論点（最大3つ）・企業と、数字と事実（ファクト RF-n。引用が本文にあれば「原文確認」）を付ける。
  - ニュース：月ごとの記事数（押すとその月に絞る）、キーワード・国内／海外・直近の追加・メモあり・質問あり・選択中・区分・月で絞る。記事ごとにメモ、ファクトの追加、「この記事に質問する」（ジョブ `research-qa`。AI が元記事を開いて読み、開けなければ検索で確かめ、どちらで答えたかを印にする）。選んだ記事は PowerPoint（一覧と1記事1枚。質問と回答はノート）に出せる。
  - 論点：論点（「論点名｜問い」で問いも持てる）ごとに、要点・主張（推進／慎重／中立と根拠の記事）・反対の見方・国内の記事・時期による変化を、記事の要約だけを根拠に AI がまとめる。新しい記事が3件たまると書き直す。
  - 技術調査・業界調査・公的データ：調査レポート（RR-n、ジョブ `research-report`）。技術は技術要素 × 文書の表・文書ごとの構成要素と処理の流れ（シーケンス図）・文書どうしのつながり、業界は広がる順の業界ごとの規模・流れ・課題・事例・制度・障壁、公的データは統計の推移・制度の動き・行政手続きのデジタル化。出典と確認日を付け、検索が使えない接続では記事集と AI の知識からまとめたことを示す。
  - 更新：見出しの「すべて更新」は1つのジョブで、記事を集めて（AI の検索・RSS・指定ページ）から、論点のまとめ（新しい記事が3件以上入った論点と古い形式のまとめ）・プレーヤーの調査と最新の動き・技術調査・業界調査・公的データのレポートを作り直す。工程はジョブの画面のグラフで見られる。各タブの「更新」（記事を更新・論点を更新・プレーヤーを更新・技術調査を更新 など）はそのタブの範囲だけを作り直す（論点は全部書き直し、調査レポートはその種類のいちばん新しいものを作り直す）。
  - プレーヤー：層ごとのマップ（最後に記事に出た日で色分け、30日の件数・姿勢）。「プレーヤーを更新」で、テーマの主要なプレーヤーを Web 検索と記事集から層・役割・取り組み・姿勢・対応規格つきで調べて足す（既にいれば空の項目を埋める）。最新の動きは「更新」のたびに登場記事から書き換える。
  - ファクトDB：種類・テーマ・国内／海外・キーワードで絞り、CSV に保存。データ分析：期間・地域・区分・論点・企業・キーワードの条件が全部に効き、概要（論点のランキングと国内／海外の割合・区分・よく出る企業）、自由集計（縦横の軸・記事かファクトか・件数か割合のヒートマップ、セルを押すと記事、CSV）、推移と増減（期間ごとの表と、直近と前の期間の割合の差）、企業・プレーヤー（企業ごとの推移・論点・一緒に出る企業、関係図）、AI に分析を頼む（根拠の記事番号つきのレポート）。定期実行はしない（画面から手で更新する）。
- ステージの AI タブの「リサーチから取り込む」：ライブラリ（と論点）を選ぶと、論点のまとめとファクトを根拠にした案を AI に頼む発言として送る（②市場分析・③競合分析での利用を想定。どのステージでも使える）。AI の案にはファクト番号・記事番号が付く。
- 「チーム」：議論（プロダクトごとのチャンネルとスレッド・メンション・通知）、チケット（TK-n。仕分け待ち→未着手→進行中→レビュー→完了）、決定記録（DEC-n）、会議と議事録（MTG-n）、ドキュメント（DOC-n）。どれも成果物の ID（US-01 など）と同じ書き方で互いを参照でき、本文中の ID はリンクになる。仕様は会話で決まることが多いので、スレッド・会議の文字起こし・外部の会話から AI が「決まったこと」と「宿題」を抜き出し、決定記録（確定待ち）とチケット（仕分け待ち）にする。人が確定した決定は、関係するステージの AI の対話に前提として渡り、ステージの参照タブにも出る。外部の会話（Google Chat・Teams・Gmail・Outlook・Meet・Slack など）はチャンネルにつなぎ、本文ごと取り込むか、要約と決定だけを残すかをチャンネルごとに選ぶ。いまは貼り付けで取り込み、Google Workspace・Microsoft 365 からの自動取り込みはこの受け口に後から足す。
- チケットと GitHub Issues の同期：プロダクトごとに「同期しない／⑫⑬（構築）のチケットだけ／すべて」を選ぶ。対象のチケットと手で起票したチケットは、作成・更新（題名・本文・完了で close）・コメントが Issue に出る。GitHub 側の close・reopen・題名の変更・コメントは、チケット画面を開いたとき（前回から1分以上）・「今すぐ取り込む」・webhook で取り込む。GitHub で作られた Issue を「仕分け待ち」のチケットにすることもできる。往復で同じ変更を繰り返さないよう、PF が書いた本文とコメントには印を付け、Issue の updated_at より新しい変更だけを取り込む。トークンはテナントごとに設定画面で入れる（暗号化して保存。なければサーバーの `GITHUB_TOKEN`）。このトークンで非公開リポジトリのコードも読める。
- 右上の歯車（設定）で、テナントが使う LLM の接続を決める。接続方式は Gemini API・Vertex AI（キー不要。Gemini と Claude）・Anthropic API・OpenAI 互換 API（ローカルLLM など）・スタブ。対話・レポート・画像でモデルを分けられる（画像は Gemini 系だけ）。アプリ全体の既定はプラットフォーム管理者（`PF_ADMIN_EMAILS`）が決め、各テナントの OWNER が自分のキーで上書きできる。API キーは `PF_SECRET_KEY` から作る鍵で暗号化して DB に置き、画面には末尾4文字だけを出す。Vertex AI（キー不要）はアプリの GCP の費用になるので、選べるのはプラットフォーム管理者と、管理者が全テナントに許したときだけ。テナントの OpenAI 互換 URL は https の公開アドレスだけを受け付ける（内部ネットワークへの到達を防ぐ）。
- 「コード（IDE）」では、プロダクトに GitHub リポジトリ（owner/name とブランチ）をつなぎ、Code-OSS の Web 版で読む（読み取り専用、ターミナルなし）。Code-OSS は `ide/VSCODE_VERSION` のタグからソースでビルドし（`ide/build.sh`）、Microsoft のマーケットプレイスや製品版の資産は使わない。IDE 内の拡張機能（`ide/extension`）が `pfrepo://<プロダクトID>/` のファイルシステムとして web の `/api/p/{id}/code/*` を読み、agent-api が GitHub の REST API から木と中身を取る。非公開リポジトリは `GITHUB_TOKEN`（読み取りだけの fine-grained token）が要る。
- ループ L1〜L5、トレーサビリティ画面、worker / scheduler は R2。
- `GOOGLE_API_KEY` が無ければ LLM はスタブ（必須見出しを埋めたダミー成果物）になり、全工程をそのまま通せる。

## ローカルで動かす

```bash
cp .env.example .env   # AUTH_SECRET と PF_INTERNAL_TOKEN を埋める
docker compose up -d --build
open http://localhost   # /register で登録すると、その人が個人テナントの OWNER になる
```

コンテナを使わない場合

```bash
# agent-api
cd services/agent && python -m venv .venv && . .venv/bin/activate && pip install -e ".[dev]"
DATABASE_URL=postgresql://pf@127.0.0.1:5432/pf PF_LLM=stub uvicorn pf_agent.api:app --port 8100
# web
cd apps/web && npm ci && DATABASE_URL=postgresql://pf@127.0.0.1:5432/pf AUTH_SECRET=dev npm run dev
```

## デプロイ（Cloud Run + Supabase）

web と agent-api（と IDE）を Cloud Run に置き、DB は Supabase を使う。リージョンは DB と揃える（Terraform の `region` と Variables の `GCP_REGION`。既定は東京 `asia-northeast1`）。nginx はローカル用で、Cloud Run では使わない。

```
利用者 ─HTTPS→ Cloud Run pf-web（公開） ─ID トークン→ Cloud Run pf-agent（IAM で非公開）
                      └────────────┬──────────────┘
                         Supabase Postgres（session モードの接続プール）
```

1. **Supabase**：Cloud Run と同じ地域でプロジェクトを作る。
   - Connect → **Session pooler** の接続文字列を控え、末尾に `?sslmode=require` を付ける（パスワードに記号があれば URL エンコードする）。
   - テーブルはサーバーからだけ使うので、Project Settings → Data API を無効にする。
2. **GCP**：課金を有効にしたプロジェクトで Cloud Shell を開き、土台を作って秘密値を入れる。
   ```bash
   git clone https://github.com/<owner>/<name> && cd <name>/infra/terraform/gcp
   terraform init && terraform apply -var project_id=<PROJECT_ID> -var github_repo=<owner>/<name> -var region=<REGION>
   gcloud config set project <PROJECT_ID>
   read -rs V && printf '%s' "$V" | gcloud secrets versions add DATABASE_URL --data-file=-     # 1 の接続文字列
   read -rs V && printf '%s' "$V" | gcloud secrets versions add GOOGLE_API_KEY --data-file=-   # Gemini を使うときだけ
   terraform output
   ```
   state は Cloud Shell の手元に残る（リポジトリには入れない）。
3. **GitHub**：Environment `production` を作る（必要なら Required reviewers を付ける）。Variables に `terraform output` の `GCP_PROJECT_ID`、`GCP_REGION`、`GCP_WIF_PROVIDER`、`GCP_DEPLOY_SA` を入れる。任意で次も入れる。
   - `PF_GEMINI=true`：Gemini を使う（無ければスタブ）。`PF_MODEL` で対話のモデル、`PF_IMAGE_MODEL` で画像のモデルを変えられる。
   - `PF_ALLOW_SIGNUP=false`：自分の登録が済んだら入れて、新規登録を締め切る。
   - `PF_GITHUB_WEBHOOK=true`：GitHub の webhook を受ける（Terraform の apply の後）。リポジトリの Settings → Webhooks に、Payload URL `https://<web の URL>/api/github/webhook`、Content type `application/json`、Secret に Secret Manager の `GITHUB_WEBHOOK_SECRET` の値、イベントは Issues と Issue comments を入れる。
   - `PF_ADMIN_EMAILS`：プラットフォーム管理者。設定画面でアプリ全体の LLM の既定と Vertex AI の利用を決められる人のメールアドレス（複数は `;` 区切り）。
4. Actions → `deploy` → Run workflow。以後は main への push で `ci` 成功後に自動で更新される。web の URL はジョブのサマリーに出る。

5. **IDE（任意）**：Actions → `ide` → Run workflow（Code-OSS のビルドに30〜60分）。終わると web に IDE の URL（`IDE_ORIGIN`）が入る。非公開リポジトリを読むときは、読み取りだけの fine-grained token を `gcloud secrets versions add GITHUB_TOKEN` で入れ、Variables に `PF_GITHUB_TOKEN=true` を入れてから `deploy` を実行する。

Supabase の session モードは同時接続数に上限があるので、Cloud Run は各サービス最大1台、DB の接続は各2本（`PF_DB_POOL_SIZE`）にしている。
