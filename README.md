# Product Factory (MVP / R0)

1人の Product Builder が、アイデアから運用まで 14 ステージ（P1〜P5、ゲート G1〜G4）を 1 つの Web アプリ上で回すための工場。
AWS Labs の AI-DLC を拡張し、Google ADK 2.x の Workflow で各ステージを動かす。設計は [docs/design.md](docs/design.md)。

## 構成

```
apps/web          Next.js 16 + Auth.js v5（テナントとロールはセッションからだけ渡す）
services/agent    FastAPI + Google ADK 2.13（ステージ実行・工場DB・監査ログ）
infra/nginx       リバースプロキシ（外に出すのは web だけ）
infra/terraform   gcp（Cloud Run の土台：Artifact Registry / Secret Manager / サービスアカウント / Workload Identity）
.github/workflows ci / infra / deploy / ide
ide               Code-OSS の Web 版（ソースからビルド）と、リポジトリを読む拡張機能
```

設計からの差分（R0 時点）

- ステージの順序とゲートは工場エンジン（決定的なコード）が持ち、各ステージの中身（質問→生成→自己監査→承認）を ADK の Workflow が 1 ステージ実行 = 1 セッションで動かす。人の入力待ち（RequestInput）は DB に残り、プロセスを再起動しても再開できる（テストで確認済み）。
- web の DB アクセスは Prisma ではなく `pg` + `apps/web/db/schema.sql`。テーブルは Tenant / User / TenantMember の3つ。Prisma のエンジン取得が開発環境から遮断されたためで、テーブルが 3 つだけなのでこのまま進める。
- 工程の順序でロックしない。どのステージからでも始められ、最新版が変わると参照している下流が「要再確認」になる。フェーズ末の審査（G1〜G4）は進行のロックではなく判断の記録。
- プロダクトごとに、ステージを使うか（開閉）と、更新に承認を求めるかを設定できる。承認の既定は個人モードがなし、法人モードがあり。
- 成果物は文章ではなく項目ごとの値（下書き）で持つ。P1〜P2 はフレームワーク（①リーンキャンバス、②TAM/SAM/SOM、③競合比較とポジショニング、④バリュープロポジションキャンバス、⑤KPIツリー・PL）、⑦は業務一覧（業務領域→業務→作業の階層と種類）とスイムレーン型の業務フロー（フローエディタ）・業務ルール・役割・例外。⑥UXデザインはペルソナ・カスタマージャーニー（ペルソナ×段階の地図。行動・接点・感情・体験の課題と機会）・ストーリーマップ（US-xx）・ユーザーフロー（UF-xx。分岐・例外つき）・受入基準（AC-xx）・画面一覧と情報設計（上位の画面・主な情報と操作）・ユーザビリティ基準、⑧は機能要求（FR-xx、ストーリーIDで⑥とつなぐ）・非機能要求（IPA 非機能要求グレードの6分類と水準）・外部接続、⑬は⑥の受入基準を取り込んだ網羅表とテストケース。ID は空なら自動で振り、⑥→⑧、⑥→⑬ の網羅を画面に出す。⑨はコンポーネント（CP-xx）・概念データモデル（ER図：エンティティ・属性の PK/FK・多重度つきリレーション）・処理仕様（PR-xx：処理区分・起動・概要・主な処理・入出力とテーブルの CRUD・リクエスト/レスポンスのパラメータ・呼び出す部品のクラスとメソッド・設定値）・状態遷移（対象ごとの状態と、イベント・条件・処理つきの遷移）・API契約・ユニット分割。CRUD マトリクス（作る処理・読む処理のないテーブルを知らせる）と、処理ごと・全体のデータフロー図は処理仕様から自動で描き、マトリクスのマスを押すとその処理の入出力に反映する。⑩は構成図（リソースを置き場所のゾーンごとに並べて通信でつなぐ）・リソース・環境・通信要件・IaC方針・月額コスト（合計を自動計算）、⑪は運用方針・運用スケジュール・起動停止・監視項目（分類別）・SLO・障害対応（重大度別）・バックアップとリカバリ（RPO/RTO）・バッチ・ログ・セキュリティ運用・CI/CD・AI評価。図はドラッグで配置を整えられ、Markdown では Mermaid（erDiagram・stateDiagram・flowchart）と表になる。以前の見出しだけの下書きは設計方針に引き継ぐ。⑫⑭は見出しごとの文書。更新すると版になり、Markdown にして下流と監査に渡す。
- 各ステージの右側でAIと対話する。AIは項目ごとの書き換え案を出し、人が採用したものだけが下書きに入る。対話の1往復は ADK の Workflow（発言と案を作る → 案を項目の型で検査して保存）で動く。
- 概要ページの上部（プロダクト名・進み具合の下）に「プロダクト・キャンバス」を置く。①リーンキャンバスと④バリュープロポジションの値（最新版を優先、なければ下書き）から画像生成AIでプロダクトの全体像（利用シーン／画面イメージ／コンセプト／グラレコ）を描き、表紙として同じテナントの人と共有する。画像は使ったプロンプトと一緒に工場DBに残す。モデルは `PF_IMAGE_MODEL`（既定 `gemini-3.1-flash-image`）、APIキーがなければ仮のSVG。既定は「自由に描く」で、書いた指示をそのまま画像モデルに渡す（画風や条件を足さない。プロダクトの内容は参考として添えるかを選べる）。できた絵は「直す」で、その絵を元に指示どおり描き直せる（新しい1枚として残り、元の絵をたどれる）。型として、利用シーン・画面・コンセプト（画風を決めてあり絵の中に文字を描かせない）とグラレコ（顧客・課題・独自の価値提案・ソリューションを日本語の見出しと短い言葉で手描き風に描かせる）もある。追加の指示は、決めてある画風や条件より優先する。
- ⑤のKPIツリーはグラフで編集する（KPIを選んで子を足す、点をドラッグして親子をつなぎ替える、分解の式 × / + を決める）。値は表と同じ行（KPI・親KPI・分解の式・目標値・計測方法）で持つので、AIの案もそのまま使える。
- サイドバーはボタンか `[` キーで隠す・表示する。右側のパネル（AIタブ・参照タブ）は `]` キーかタブで開閉する。どちらも状態は cookie に残す。
- AIタブの対話はセッションに分けられる（新しく始める・切り替える・名前を変える）。各セッションは ADK のセッションと1対1。「レポート」でステージの全セッションを要約・決まったこと・却下した案・未決事項にまとめる。
- 参照タブでは、事業フェーズ（①〜⑤）の成果物（最新版、なければ下書き）をその場で読める。
- 文書タブは編集できる。「## 項目名」の見出しごとにキャンバスの項目へ反映する（フローなど文書から読めない項目は変えない）。
- 「確定」ではなく「更新」と呼ぶ。下書きを更新すると版が1つ増え、その版が最新版になる。
- フレームワーク（工程＝基本の項目＋足したフレームワーク）：各工程は基本のフレームワーク（①リーンキャンバス・②TAM/SAM/SOM など）に、ライブラリのフレームワークをいくつでも足して組み合わせる（工程の画面の「フレームワークを足す」。必須にもできる）。標準のライブラリは PEST・ファイブフォース・3C・STP・SWOT・クロス SWOT・VRIO・戦略キャンバスと ERRC・ポジショニングマップ・バリューチェーン・アンゾフ・4P・ビジネスモデルキャンバス・ステークホルダーマップ・ユニットエコノミクス・損益分岐点・シナリオ分析・OKR。新しいプロダクトには ②PEST とファイブフォース、③ERRC と VRIO、④SWOT・クロス SWOT・アンゾフ、⑤ユニットエコノミクスと損益分岐点を最初から足しておく（必須ではない）。フレームワークは部品（文章・箇条書き・表・2×2 の象限・ポジショニング図・ノードと線の図）を 12 列の格子に並べて定義し、エディタ（`/p/{id}/frameworks`。管理者だけ）で独自のものを作る・標準を上書きできる（部品はドラッグで動かし、角で大きさを変える）。足したフレームワークの部品は工程の項目（`<フレームワーク id>.<部品>`）として扱い、下書き・承認・AI（担当・PM・チャット）・Markdown・下流の工程・報告資料・資料の取り込みがすべて読む。
- スマホ専用の UI：スマホ（User-Agent。cookie `pf_view` で切り替え）で開くと、同じ URL のまま middleware が `/m` 以下のスマホの骨組みに回す。上のバー（≡ のメニュー：このプロダクトの工程・UI のプロトタイプ・プロダクトの切り替え・PC 版）と、どの画面にも下にある入力欄（あらゆる指示の起点。上に「話題」があり、押すとプロダクト全体・工程・UI のプロトタイプから選べる。＋で @ と添付）。ホームは チャット｜承認｜進捗（ファクトリー全体では チャット｜承認｜プロダクト）。工程は成果物を文書として全画面で読み、UI のプロトタイプは触る・部品にコメントして AI に送る（下から欄が出る）、Issue は中身と経過を読む。全画面の表示で話すと、チャットが下から出て答えと承認依頼が見える。部品・フレームワークのエディタ・IDE などの細かい編集の画面は「PC 向けの画面です」と出し、PC 版で開ける（PC 版にはスマホ版に戻すボタンが出る）。
- UI（⑥）はプロトタイプだけ（`/p/{id}/s/s06/ui`）：画面の移り方まで操作できる「1つの HTML」（案内（シナリオ・画面の一覧・設計メモ）＋端末の枠＋JavaScript の画面遷移）。⑥の「UI デザイン」の `proto` に入る。画面ごとの部品のエディタは廃止した（前に作った画面ごとの UI は `pages` に残り、「これまでの画面からまとめる」でプロトタイプにできる）。工程のエージェント・自動開発・取り込みは UI を書かない（人の編集・チャットの承認・プロトタイプの保存だけ）。作り方は「AI で作る」（ジョブ `ui_proto`。⑥の画面一覧・ユーザーフローから書き、できたら設計PM がチャットで下見つきの承認依頼を出す）と「HTML を取り込む」（手元のモックアップ。script もそのまま動く）。表示は隔離した枠（`sandbox="allow-scripts"`・別オリジン）の中だけで、差し込む CSP で外への通信・外部の script を止める（フォントは Google Fonts だけ許す）。見え方は「収める」（中身の実際の幅（1000px より広ければその幅）で描いて、枠に収まるよう縮める）・「100%」（そのままの大きさ。はみ出したら横に送る）・「スマホ」（390px）。「大きく見る」で画面いっぱいに出し（Esc で戻る）、右の欄（コメント・作る・コード）はたためる。「コメント」で部品を押すとコメントを付けられ（位置・部品・いまの画面を残し、番号のピンが付く）、AI に送ると設計PM が一部だけの書き換え（`ui_proto` の edits）の承認依頼を出す。UI のページで話すと、いつもプロトタイプについての指示になる。承認すると直り、送ったコメントは「反映済み」になる。コードを直接直す・HTML をダウンロードすることもできる。⑥の工程とプロダクトレビューには、プロトタイプの下見が出る。
- 承認待ちの案（ダッシュボード）：各エージェントから届いた工程の書き換え案（資料の取り込みの案、定期の仕事の案など）を、工程ごとにまとめて1か所に並べる。案ごとに差分を見せ（表は列見出しつきで、追加した行・削除した行・変わったセルに色を付け、変わっていない行はたたむ。文章は文ごと、箇条書きは項目ごとに追加・削除を示す。「2行変更・1行追加」のように要約も出す）、「承認」したものだけ工程の下書きに入れる（「否認」なら何も変えない）。工程ごとにまとめて承認もできる。工程の画面には案・参照の欄はない。
- チャット（ファクトリー全体で1つ）：どのページでも、右端のチャット欄に対話と、その下に入力欄が出る（エージェントごと・ページごとのチャット欄はない。閉じると右上のボタンだけになる）。対話はプロダクトごとで、プロダクトのページではそのプロダクトの対話だけ、プロダクトの外のページ（ホームなど）ではファクトリー全体の対話だけを出す。何も指さずに書くと、いま開いているページについての指示・質問になる（工程のページならその工程、Issue のページならその Issue）。@ で工程・ページ・機能・エージェントを指すと、開いていないものについても話せる（候補から選ぶ）。文に工程の番号・名前があれば、その工程の話として扱う。答えるのは PdM が話せる相手だけで、工程・領域のことはその領域の PM、稼働・スケジュール・ペルソナ・組織の設定はプラットフォーム（入力欄の上に「話題」と「答える人」を出す）。プロダクトのページでは資料・画像を添付でき、工程のページではリサーチライブラリを根拠として添えられる。何かを変えるときは、答えに承認依頼（変更前と変更後）が付き、「承認」したものだけをコードが確かめてから実行する（「否認」なら何も変えない）。変更の種類は、工程の項目の書き換え・工程の確定（今の下書きを新しい版にして「更新済み（完了）」にする。PM から。必須が空の工程は出せない。承認が要る工程も、チャットで PdM が承認したらそのまま承認する。下流は「要再確認」になる）・担当への Issue の起票（PM から）・Issue の更新・予定の変更・エージェントを止める／動かす・稼働の問題への対処。答えの本文は、承認前の変更を「更新しました」と書かず「承認依頼を出しました」と書く。出せなかった変更（ない項目への書き換えなど）は、答えの先頭に「何も変えていません」と出す。PM が答えたものは PM の作業場所と会議の記録にも残る。AI（PM・プラットフォーム）から PdM に話しかけるのは4つの型だけ：質問・相談・ネクストアクションへの合意依頼・タスクの終了承認依頼（`asks.py`。報告・共有だけの書き込みはしない。型に合わないもの・合意依頼で次のアクションがないもの・終了承認依頼で開いた Issue がないものはコードが出さない）。テナントの全員のチャットに型の印つきで届く。質問・相談には「◯◯に返事をする」で答える（元の発言を引用して入力欄に入れ、送ると引用つきの発言として残る。宛先は元の発言の PM になり、PM は何への返事かを読んで答える。PM の対話の記録にも引用が残る。引用は×で外せる）。合意依頼は「合意する／合意しない」、終了承認依頼は「終了を承認／否認」で答え、答えは PM 宛ての Issue（または該当の Issue の記録）になって PM か担当がすぐ動く（否認しても止まらない）。プラットフォームは、対処があれば合意依頼、なければ相談として知らせる。同じ問いかけは重ねない：PdM がまだ答えていない同じ PM からの問いかけ（24時間以内。合意依頼・終了承認依頼はボタンに答えるまで、質問・相談はその PM に PdM が書くまで）と文字の重なりが35%以上なら出さない（担当が何人も同じことを上げても、PdM に聞くのは1回）。PM には未回答の問いかけを見せ、同じことを聞かないようにする。ツールで読めないことを権限の問題として PdM に聞かない（工程の下書きは stage_draft でどの工程でも読める。上流が確定していなければ upstream は今の下書きを返す）。⌘K の「チャットで◯◯に話す」は、宛先をメンションにして入力欄に入れる。工程の担当と直接話す古い API（`/products/{id}/stages/{sid}/chat`・`/sessions`）は閉じた（410 を返す）。工程の画面には案・参照の欄はない。 すべてのエージェントの書き込みに「返事をする」（引用つき）が付く。PM・プラットフォームの書き込みにはそのエージェントが、工程の担当・リリースエージェントの書き込みには窓口の PM が答える。
- スケジュール（`/p/{id}/schedule`）：エージェントが定期的に動く予定を、cron を書かずに選ぶ（◯分ごと・◯時間ごと・毎日・平日・曜日を選ぶ。詳しい設定として cron も書ける）。選ぶたびに読み方（「毎週月・水曜 9:30」）と次の3回を出し、10分より短い間隔には注意を出す。PM・領域ごとの担当・会議をまとめて選んで同じ予定にする・止める・動かす。これから24時間の時間割（横が時刻、行がエージェント。動く時刻を縦線で、1時間に4回以上動く予定は帯で示し、いまの時刻とカーソルの時刻に線を引く）と、すべてのプロダクトの予定（グループごとの予定・止めている数・次の時刻）を並べる。プラットフォームの見回りの間隔（1・5・10・15・30・60分、テナントごと）もここで変える。エージェントの組織の画面の設定も同じ選び方。毎分の呼び出し（Cloud Scheduler）は固定。
- ペルソナ・スキル・ツール（テナントで共通の配役。画面は `/p/{id}/cast`、変えられるのは管理者）：エージェントごとにペルソナ（役割名・性格・大事にすること・話し方・得意・気をつけること。⑥の担当は UX デザイナー）と、直結するスキル・使ってよいツールを割り当てる。スキルは2種類：エージェントに直結するスキル（その役割の手順と判断の基準）と、参照スキル（共通の知識を小さく分けたもの。直結するスキルが参照したときだけ読み込む。深さ3・12個・2.4万文字まで、同じものは1回）。1つのスキルは8000文字までで、長くなるものは参照スキルに分ける。固定のロジックはツール（`tools.py`）にし、スキルが名前で呼ぶ：読むツール（工程の下書き・項目の定義・上流の確定版・取り込んだ資料を読む／探す・Issue・掲示板・網羅の計算・CRUD マトリクス・ファクトリーの稼働状況）は AI が必要なときに呼ぶ（1回の実行で6回まで。スキルの prefetch に書いたものは AI を呼ぶ前に読む）。書くツール（項目への書き込み・Issue の更新と起票・掲示板・PM の記録・修正の提案）は AI が最後の出力に入れ、コードが型・宛先・権限を検証してから実行する。使えるツールは「割り当てたツール ∩ 読み込んだスキルが使うと書いたもの ∩ 役割で使えるもの」で、スキルが使うのに割り当てていないツールは警告に出る。標準のスキル（`services/agent/pf_agent/skills/*.md`）はリポジトリで管理し、テナントは画面でスキルを作る・標準を上書きする（消すと標準に戻る）。参照が輪になるスキルは作れない。ジョブの記録には、使ったスキルと読んだツールが残る。
- エージェントの組織：PdM（人）と、事業 PM（①〜⑤）・設計 PM（⑥〜⑪）・実装 PM（⑫〜⑭）、①〜⑭の担当。PdM が話せるのは PM（とプラットフォーム）だけで、担当とは直接話さない（話すのは右のチャット。担当には PM が Issue で伝える）。各担当も PdM に直接話しかけず、自分の領域の PM に上げる。PM は1時間ごとに領域の担当へ状況確認を出し（掲示板の「定時の状況確認」スレッド。領域の担当は全員が今の状況を返事し、変わっていない担当は「前回から変化なし」と添える。最後に PM が返事の数と変化のあった担当をまとめる）、集めたことを PM のタスク管理の場所（PM の作業場所）に残す。AI を呼ぶのは変化か PM 宛ての Issue があるときだけ。各工程の担当は10分ごとに自分宛てで終わっていない Issue を確かめ、あれば実行計画を立てて実行し、工程の下書きに書き込み（変えた項目は Issue の記録と監査ログに残る）、状態・進捗率を更新して起票した人か確認が要るエージェントに返す。なければ AI は使わない。承認者の修正指示（Request Changes）は、その領域の PM から担当への Issue になる。
- Issue（#n。Redmine と同じ形）：トラッカー・状態（新規・進行中・解決・フィードバック・終了・却下）・優先度・担当・起票者・開始日・期日・進捗率・親、更新ごとの記録（注記と属性の変更前後）。宛先は PM と各工程の担当まで（PdM は宛先にできない）。PdM が起票・書き込みできるのは PM 宛ての Issue だけ。起票・付け替え・書き足しをすると担当にすぐリクエストが飛ぶ（担当は10分ごとの確認でも拾う）。GitHub Issues との同期は人が押したときだけ動く（自動では送らない・取りに行かない）：Issue の画面の「GitHub に送る／GitHub と同期」と、一覧の上の「今すぐ同期」（つないだ Issue すべて。選べば、まだつないでいない開いている Issue も送る）。同期すると、GitHub 側のコメントと開閉（前回の同期から GitHub で変わっていれば GitHub を正とする）を記録に取り込み、こちらの題名・本文（説明と状態・担当などの要約）・開閉と、まだ送っていない記録（注記と属性の変更）をコメントで送る。GitHub でコメントがあれば担当を動かす。プロダクトにリポジトリ（コード）とテナントのトークン（設定）が要る。
- サイクルの計画（PdM が決める。レビュー画面の「サイクルの計画」）：サイクル数と、各サイクルの位置付け（例：1＝PoC用プロトタイプ、2＝MVP、3＝MMP）・目的・終える条件を並べる（12まで。「例を入れる」で PoC→MVP→MMP）。決めていなければ、作ったときの範囲（MVP・PoC）を1サイクル目にする。今のサイクルの位置付けは、PM の計画づくり・担当・PM の定時確認の指示に入り（作り込みの深さを位置付けに合わせる）、ダッシュボード（「サイクル 1：PoC用プロトタイプ（全 3）」）と工程の画面に出る。計画は今のサイクルより短くできない。計画の最後を超えて次のサイクルを始めるときは、位置付けを書くと計画に足す（計画を決めていなければ、位置付けなしでも進める）。
- Markdown の表示（`components/md/Md.tsx`）：レビュー画面・工程の文書タブ・ドキュメント・プリプロダクト・会議で共通。表などの GFM に加え、```mermaid のコードブロック（業務フローなど）を Mermaid（11.4.1、MIT。使うときだけ読み込む。securityLevel は strict）で図にする。描けない記法は、理由と元の記法をそのまま見せる。
- 事実と作り話の対策（`facts.py`・`refs.py`・スキル facts-and-authority）：AI が起きていない状態の変化（デプロイした・本番で稼働・承認した・確定した・マージした・テストが通った・成果物を書いた など）を書かないよう、DB から取った「システムの状態（事実）」（サイクル・工程の状態と版・リリースとリリース系のジョブ・プロダクトレビューの回・PdM の判断・最近のジョブ。リリースがなければ「行われていない」）を ID つきで担当・PM・PM 同士の連絡・チャットの指示に入れる。根拠の ID は `種類:キー` の形で、参照の登録簿（`refs.py`）が種類ごとに実在と状態を解決する：job（ジョブ）・issue:#n・note:n（PM の記録）・report:key（担当の報告）・post:n（掲示板）・stage:sNN（工程の状態と版）・field:sNN.項目（成果物の項目に中身があるか）・msg:n（PdM の判断）・review:cNrM（プロダクトレビューの回）・pr:#n（プロダクトのリポジトリのプルリクエスト。GitHub に聞く）。AI が状態の変化を書くときは evidence に ID を入れさせ、LLM を使わずに照合する：文ごとに「系統の単語」と「完了の言い方」がそろった文を主張とみなし（否定・予定・質問・依頼は除く）、系統ごとに通る根拠を決めている（リリース・デプロイ・本番の稼働＝成功したリリースのジョブ、承認＝PdM が承認した記録・確定済みの工程・成功したリリース・完了したレビュー、確定＝確定済みの工程、マージ＝マージ済みの pr、テスト＝成功したジョブ・⑬の結果・マージ済みの pr、レビューの完了＝結果の出た回・PdM の判断、成果物の更新＝中身のある項目・工程・Issue・報告・記録）。担当がその実行で書き込んだ項目と更新した Issue は自動で根拠に足す。照合できない投稿（PM 同士の連絡・掲示板）は載せずに PM の記録に残し、担当の報告からは外して unverified に残し、Issue の注記・PM の記録・チャットの返事は「［根拠なし・未確認］」の印を付けて残す。PdM への話しかけからは外す。PM・担当にはリリースの承認権限がない（PdM だけ）ことを指示に入れる。
- サイクルとプロダクトレビュー（`cycles.py`、画面は `/p/{id}/review`）：1サイクル＝使っている①〜⑬の工程が100%になるまで（⑭リリースはサイクルの外。上流の工程とはつながらず、⑪⑬が変わっても「要再確認」にならない。⑭の担当＝リリースエージェントは実装 PM の領域にも入らず、PM の定時確認・PM 同士の連絡・振り返りの会議・サイクルの目標の対象外。Issue・質問の窓口だけ実装 PM。下のリリースで扱う）。工程の%は、確定済み（更新済み）なら100、そうでなければ担当の報告の進み具合（必須が空なら99まで）で、ダッシュボードの進み具合はその平均。①〜⑬が100%になると、定期実行の中で自動でプロダクトレビューに入る（PdM が先に始めることもできる）。プロダクトレビューは振り返りの会議のように回で進める：各 PM が自分の領域の成果物をレビューして指摘（工程・重さ・何が問題か・直し方）を出す（ジョブ product_review）→ PdM が PM のレビューと①〜⑬の成果物を読み、要れば PM ごとに修正を指示する → PM が担当に Issue（バグ・高め）を出し、担当がすぐ直す → 修正の Issue が全部終わると知らせる → もう一度 PM にレビューさせる …。納得したら PdM が完了にし、リリースに進む（オンボーディング）か、リリースせずにサイクルを終える。サイクルが終わると（done）、PdM が次のサイクルの戦略（必須）と PM ごとの追加指示を書いて次のサイクルを始める：工程の%を0に戻し（下書き・版は残す。作り直しではなくエンハンス）、まず PM が戦略と追加指示に沿って領域の工程ごとに目標・計画・完了の条件を決め、担当に Issue を出す。担当はその Issue を受けてすぐ動く。サイクル実行中以外（レビュー・リリース・次のサイクル待ち）は、エージェント・PM 同士の連絡・会議の定期実行と「今すぐ動かす」を止める（予定の時刻だけ進める。プラットフォームも遅れとは扱わない）。レビューの修正・リリースの作業は、それぞれのジョブと Issue で動く。担当と PM のプロンプトには、このサイクルの位置付け・戦略・目標が入り、工程の画面にも目標が出る。これまでのサイクル（位置付け・戦略・所見）はレビュー画面に残る。
- リリース（`releases.py`、画面は `/p/{id}/release`。サイクルの外）：プロダクトレビューを完了してリリースに進むと、オンボーディングに入る。リリースエージェント（⑭の担当）が、インフラ設計（⑩）・運用設計（⑪）・コード（⑫）・テスト（⑬）と接続先を読み、リリース先の環境（クラウド・オンプレミス・ハイブリッド・SaaS と事業者・場所・構成）・リリース方式（一度に切り替え・ローリング・ブルーグリーン・カナリア・手動）・手順・設定（秘密の値は書かない）・リリース後に確かめること・切り戻し・リスクを定義する（ジョブ onboarding）。PdM はリリース前レビューで定義を読み、直させる（指摘を渡してもう一度定義させる。前の定義は履歴に残る）か、リリースを承認する。承認すると、リリースエージェントが接続先でデプロイ・設定を行う（ジョブ release）：GitHub Actions（プロダクトのリポジトリのワークフローを workflow_dispatch で起動。選べばリリースの定義を inputs の pf_cycle・pf_plan で渡す。テナントの GitHub トークンを使う）・Webhook（https・外部のアドレスだけ。リリースの定義を JSON で送り、署名の鍵があれば x-pf-signature に HMAC-SHA256 を付ける。CD の仕組みが受ける）・手動（手順書のとおりに人が作業し、PdM が完了にする）。このファクトリーが直接クラウドの API を叩いてデプロイすることはしない。リリースできたら⑭の「デプロイ記録」に追記し（「監視設定」が空なら確かめることを入れる）、サイクルを完了にする。失敗したらリリース前レビューに戻り、接続先を直して承認し直すか、定義を直させる。
- 掲示板：プロダクトの進み具合について、他のエージェントに確認が要ることを伝え合う場所（確認・回答・共有。エージェント同士だけで、PdM は読むだけ）。動く必要があることは Issue で管理する。確認と回答は、書き込んだ時点で宛先がすぐ動いて読み、確認にはそのスレッドで答える（工程の担当も、手を動かす Issue がなくても動く。共有は次に動くときに読む。定期実行でも未読の確認を拾う）。往復が止まらないよう、回答への返事は書かせず、長くなったスレッド（7件以上）の回答では相手を起こさない。Issue・掲示板で起こされた PM は、定時の状況確認は出さずに答えるだけ。エージェントは期限・時刻（「本日15時までに」など）を書かない（受けた相手はすぐ動くため。プロンプトにいまの日時を入れ、書かれた期限はコードが取り除く）。
- PM 同士の連絡（既定は10分ごと・5分から。担当の確認の0・10・20…分と重ならないようずらしている。スケジュールで変えられる）：事業・設計・実装 PM が、前回からの PM の記録・領域をまたぐ開いた Issue・担当の報告を材料に、他の領域に関わること（依存・前提の食い違い・相手の判断が要ること）だけを掲示板の「PM 同士の連絡」スレッドに書く。確認を受けた PM はすぐ動いて答える。材料が前回から変わっていなければ AI は使わず何も書かない。
- 振り返り：1日1回の振り返りの会議と、工程のゲート（G1〜G4）は、サイクルとプロダクトレビューに置き換えて廃止した（レール・道具・ダッシュボード・予定から外し、会議の API は 410 を返す。会議の予定は止める。データは残す）。
- 定期実行は必ず動かす：Cloud Scheduler が毎分 `/internal/scheduler/tick` を呼ぶ。時刻が過ぎた予定は次の呼び出しで1回動き、起動に失敗したら時刻を戻してやり直す。画面を開いていないプロダクトにもエージェントを置く。AI の呼び出しには上限時間（10分）と再試行を付け、時間を過ぎても終わらないジョブは失敗にして理由を残す。最後に呼ばれた時刻と各担当が最後に確かめた時刻を画面に出す（ダッシュボード・エージェントの組織）。
- ダッシュボード（プロダクトのトップ）：組織と工程のグラフ（PM を領域の真上に置き、担当ごとの健全度・進み具合・報告・自分宛ての Issue・各案。工程のつながり、指揮系統、この7日の掲示板と Issue のやり取りを線で）と、案ごとのグラフ。PM との対話・今日の振り返りの会議・対応が必要な工程・定期実行の状態を並べる。
- プラットフォームエージェント（プロダクトごと）：そのプロダクトが動いているかを見張り（問題・対話・稼働状況・レールの印はそのプロダクトの分と、定期実行の停止のようなテナント全体の分だけ。テナント全体の重い問題は各プロダクトのチャットに知らせる。見回り自体と間隔の設定はテナントでまとめて行う）、PdM と直接話す（PM・担当とは別の存在。プロダクトの中身ではなく処理系を見る）。AI を使わず記録から決まった規則で問題を見つける（定期実行から5分ごと・画面を開いたとき）：定期実行（tick）が来ていない・止まっている、ジョブが始まらない、ジョブの失敗（種類・プロダクト・原因ごと。最後に成功してからの回数。LLM の利用上限・認証の失敗は重く扱う）、担当が拾っていない Issue（担当は30分・PM は2時間が目安）、やり取りが往復し続ける Issue、期日を過ぎた・3日以上動いていない Issue、予定の時刻を過ぎても動いていない・次の予定がないエージェント、止めているのに Issue を抱えたエージェント、詰まっていると報告している担当。同じ問題は1件にまとめ、見つからなくなったら自動で解決にする。重い問題が新しく出たら PdM に知らせる（対処があれば「ネクストアクションへの合意依頼」、なければ「相談」）。対処は「承認して実行」したものだけ動く（定期実行を1回動かす・担当を動かす・予定を立て直す・止めたエージェントを再開する）。対話では稼働状況と問題を材料に答え、運用の対処と処理系（コード）の修正案を出す（コードは自分では直さない）。画面は `/p/{id}/platform`（稼働状況・問題・プロダクトごとのエージェントの実行状況・ジョブ・対話）、⌘K の「@プラットフォーム」でも話せる。
- ナビゲーション（エージェント時代）：左のレールはページではなく「人」を並べる。いちばん上にプラットフォーム（未対応の稼働の問題の数）、続いて3人の PM と各工程の担当が顔と状態（作業中＝回る輪・PdM の返事待ち＝脈打つ・止まっている＝赤・閉じている＝薄く）・未読・報告の一言で並び、押すとその担当の部屋（工程の画面と対話）に入る。工程グループ（事業・要求設計・構築・リリース）は色で分ける。レールは5秒ごとに状態を読み直し（画面を開いている間だけ。どのページでも）、「状態の更新 時:分:秒」と定期実行が最後に来た時刻を出す（読めないとき・定期実行が5分以上来ていないときは赤）。道具（プロダクトレビュー・リリース・Issue・掲示板・ドキュメント・ジョブ・設定など）はレールの下に、アイコンと名前を1列で縦に並べる。⌘K（どこからでも）で行き先を言葉で探すか、そのまま PM に話しかける（「@⑨ 状態遷移に取消を足して」は⑨の領域の設計 PM に「⑨について」話す。PM はその場で答え、要れば担当に Issue を起票する）。読み違えないよう、行き先も相手も候補として見せ、選んだものだけを実行する。
- エージェントの顔：3人の PM と各工程の担当を、同じ画風のイラストにする（画像生成AI。テナントで共通の配役、エージェントの組織の「顔を描く」でジョブ avatars）。描いていない担当や描けない環境では、役割から決まる人物のイラスト（肌・髪型・髪色・服・眼鏡やヘッドセットなどの持ち物・背景の色を役割ごとに決めてある）を出す。顔はレール・ダッシュボードのグラフ・掲示板・Issue・PM との対話に出る。
- 工程の担当（その分野の専門家）との相談：工程の画面の「担当に相談」（`/p/{id}/s/{sid}/consult`。スマホも）か、チャットで @⑥UXデザイン担当、相談の発言への返事で、PdM は工程の担当と直接話せる（PM を通さない）。担当は知識の束（`services/agent/pf_agent/knowledge/{sid}.md`。いまは⑥UX だけ厚く用意。ほかの工程はスキルと AI の知識で答える）と工程の中身をもとに、問いを立てて導き、原則・手法を名前で挙げて選択肢と推しを出し、弱い前提は率直に指摘する。PdM が決めたことは「合意メモに残す」承認依頼（`consult_note`）にし、承認すると合意メモ（`consult_notes`）に残る（手で足す・消すこともできる）。合意メモは、その工程の担当が動くとき（定期実行・チャット）に必ず読む（下書きはこれと食い違わせない）。「合意メモから下書きを作ってもらう」で項目の下書き（set_field）を頼める。相談の部屋では右のチャットは出さない（部屋そのものがチャット）。
- 成果物の書き出し：工程の画面（PC・スマホ）の「書き出す」から、成果物を Word（.docx。見出し・表・リスト・引用・コード）・PowerPoint（.pptx。表紙＋見出し（##）ごとに1枚、多いときは続きのスライド、表は表のまま10行ずつ）・PDF（印刷用のページ `/print/p/{id}/s/{stage}` を開き、印刷の画面で PDF に保存。Mermaid の図も入る）・Markdown（.md）にする。Word・PowerPoint はブラウザの中で作る（docx・pptxgenjs）。Word・PowerPoint では Mermaid の図はコードのまま入る。
- チャットの手ざわり：送るとすぐ自分の発言が出て入力欄が空になる。答える人と、していること（読んでいる工程・ツール・根拠の確かめ・承認依頼の用意）が順に出て、返事の文章は流れてくるまま出る（`POST /assistant/messages/stream` が NDJSON で user・route・step・delta・reset・done・error を流し、web の `/api/assistant/stream` が中継する）。AI には返事の文章のあとに `<<<JSON>>>` と承認依頼・根拠の JSON を書かせ、文章だけを流す（JSON が崩れたら決まった形で作り直し、出し直す）。返事は Markdown で出す。送れなかったら入力欄に戻してわけを出す。
- 対話への添付：PM との対話に、資料（Excel・Word・PowerPoint・テキスト）や画像をクリップ・ドロップ・貼り付けで添えられる（1回5個まで）。添えたものはその発言のときだけ AI が読み（資料は文章にして、画像はそのまま。画像を読める接続のとき）、工程の値や取り込んだ資料にはならない。履歴には名前だけ残る。 HTML（html・htm。1.5MB まで）も添えられる：ソースのまま持ち、AI にはソースで渡す（長いときは先頭の10万文字）。⑥の UI で「この HTML をプロトタイプにして」と頼むと、添付の HTML をそのままプロトタイプにする承認依頼が出る（Shift_JIS・EUC-JP の HTML も読める）。
- 資料の取り込み（ドキュメントのページから）：手元の Excel・Word・PowerPoint（.xlsx .docx .pptx）やテキストを上げると、中身を文章にし（Excel はセルと図形の文字、Word は見出しと表、PowerPoint はスライドごと）、ジョブ（import）が「どの工程のどの項目にあたるか見分ける → 工程ごとに項目の値を抜き出す → 入れる」を行う。入れ方は「AI の案として出す」（ダッシュボードの「承認待ちの案」に「資料の取り込み：ファイル名」として案が並び、承認したものだけ入る）か「空の項目には直接入れる」（値がある項目は上書きせず案にする）。資料に書かれていないことは入れない。割り当て先の工程は絞れる。取り込みが終わると、割り当てた工程の担当に掲示板で知らせ、担当は動くときと PdM と話すときに、資料のうち自分の工程の項目名・工程名がよく出てくる章を読む（PM は資料の一覧と割り当て先・冒頭を読む）。資料ごとに「読んでいいエージェント」を割り当てられる（既定は割り当てた工程の担当と、その領域の PM。全員・誰にも読ませない、も選べる）。手で書いたドキュメント（DOC-n）も同じように読む（既定は全員。ドキュメントの画面で「読んでいいエージェント」を絞れる）。読むツール docs_read・docs_search は、取り込んだ資料と手書きのドキュメントの両方を対象にする。
- 報告資料（RP-n）：各工程の企画情報から範囲（工程→項目。まとめ選びあり）を選び、題・読み手・目的・枚数を決めると、ジョブ（report）が「集める→構成と本文を作る→表を付録にする」を行う。本文は1枚1メッセージで根拠の工程を持ち、表・処理仕様（CRUD マトリクス）・ER・構成図は付録の表にそのまま付ける（12行で分ける）。使う中身は最新版（なければ下書き）か下書き。画面でスライドを直し・並べ替え・足し引きして、PowerPoint（ノート付き）と Markdown に書き出す。
- 自律エージェント（AG-n）：cron（分 時 日 月 曜日、日本時間。よく使う形はボタン）で仕事を予定する。仕事は「工程の見直し」（選んだ工程を上流の最新版と突き合わせ、食い違い・必須の抜け・根拠のない数値・古い前提を探す）・「自由な指示」・「リサーチライブラリの更新」・「報告資料の作り直し」。見直しと指示はジョブ（agent：工程を読む→見直す→受け箱に出す）で動き、見つけたことは受け箱に提案（重大度・根拠・項目の直し案）として届き、予定を作った人に通知する。提案は「採用して入れる（案を選べる）・確認済み・却下」にするか、返信して AI と詰める（AI が答え、必要なら案を直す）。AI が工程の値を直接書き換えることはない。時刻の判定は `/internal/scheduler/tick`：Cloud Run では Cloud Scheduler（pf-agent-tick、毎分、pf-web の SA の ID トークン）が呼び、手元では `PF_SCHEDULER=thread` でプロセスの中で1分ごとに回す。次の時刻を書き換えられた方だけが動かすので、二重には動かない。「今すぐ」でいつでも動かせる。
- 各ステージの「以降の工程を自動開発する」：上流（押したステージまでの最新版、なければ下書き）に従って、AI が違いのはっきりしたパターン（案）を決め、案ごとに後工程（⑪運用方式設計まで）の下書きと、ブラウザで触れる単一ファイルの試作を作る。できたものはプリプロダクト（PP-n）として残り、並べて比べ、試作を触り、1つを採用すると各ステージの下書きに入る（人がそこから直して更新・承認する）。試作は sandbox の iframe で、通信なしで動かす。作ったあとで上流の版が変わると知らせる。各ステージの画面の上部に「本線／PP-n 案…」のタブが出て、案ごとのそのステージの下書きを本線と同じ見た目で読める。工程ごとに「この工程だけ本線に取り込む」で案を選び分けられる。採用した案を実コードにして Cloud Run に展開するのは次の段。
- ジョブ：自動開発のような時間のかかる処理は、Cloud Run Jobs（`pf-autodev`。agent と同じイメージで入口だけ `python -m pf_agent.worker <job_id>`）で動かす。手元・テストでは裏のスレッド。右上の「ジョブ」（プロダクトのサイドバーからも）で、ジョブの定義・実行中の一覧・グリッド（実行 × 工程の状態、Airflow のグリッドにあたる）・実行履歴・使った LLM のトークン量（モデル別）を見て、取り消し・作り直しができる。ジョブの中は依存関係つきの工程（自動開発：パターンを決める → 案ごとの後工程 → 試作、リサーチ：検索・RSS → 記事を読む → 論点のまとめ）に分けて記録し、ジョブの画面で工程のグラフ・ガント・一覧（状態・時刻・所要・工程ごとのトークン・失敗の理由）を見られる。自動開発を始めると、このジョブの画面に移る。
- 新しいプロダクトは、トップの「新しいプロダクトをつくる」から AI の聞き取りで作る。AI が1〜2問ずつ聞き、分かったこと（名前・作るもの・誰のためか・困りごと・解決のしかた・選ばれる理由・MVP か PoC か）を右にまとめる。人が右で書き換えた項目は AI が上書きしない。作ると、答えた内容が①リーンキャンバスの下書きに入り、続けてプロダクト・キャンバスの最初の1枚（表紙）をジョブ（`canvas`）で裏で描く。聞き取りの途中は保存しない。
- 社内のオントロジー（右上の網の目のアイコン）：社内の用語・組織・役割・業務プロセス・システムと、その関係（〜の一種・〜の一部・〜が担当・〜を使う・〜の前に行う・関係する）をテナントで1つ持つ。一覧とグラフで編集し、ドキュメント（書いたもの・取り込んだ資料）から AI が用語の候補を出す（人が承認したものだけが使われる）。AI は、扱う文章（ステージの対話・自動開発の上流・会話からの抜き出し）に名前か別名が出てくる概念と、その周り1段の関係だけを前提として受け取る。何が渡るかは画面で確かめられる。書き出し・読み込みは SKOS（W3C の語彙の標準）の Turtle と JSON-LD（rdflib）。
- リサーチライブラリ（右上の本棚のアイコン）：トピックごと（RL-n）の資料室。タブは「ニュース・論点・技術調査・業界調査・公的データ・プレーヤー・ファクトDB・データ分析」。
  - 集める：「更新」はジョブ（`research`）で、前回の最新記事より後の記事を AI の検索・RSS / Atom・指定したページから集める（1回60件まで、公開アドレスだけ。転送先も確かめる）。AI の検索は、接続が Claude（Anthropic API・Vertex AI）なら Claude をエージェントとして動かし、期間を最大12に区切って、区切りごとに Web 検索（Vertex AI は `web_search_20250305`、Anthropic API は `web_search_20260209`。1回8検索まで）を繰り返させ、見つけた記事を伝えて「まだ見つけていない記事」を探し直す（新しく3件未満になったら次の区切りへ）。Gemini の接続でも同じく、期間を最大12に区切って区切りごとに Google 検索グラウンディングを最大3回まで探し直させ（1件1行で書かせ、出典の対応から URL・見出し・日付を取る）、論点・企業の切り口でも1回ずつ探す。記事への質問と調査レポートの下調べも同じ接続の Web 検索を使う。本文を開けない記事は検索結果の文章から作り「本文未確認」にする。期間の始まりを決めていれば毎回そこから探す（URL で重ねない）。手で URL か本文を足すこともできる。記事（RA-n）ごとに日本語の見出し・要約・国・区分・論点（最大3つ）・企業と、数字と事実（ファクト RF-n。引用が本文にあれば「原文確認」）を付ける。
  - ニュース：月ごとの記事数（押すとその月に絞る）、キーワード・国内／海外・直近の追加・メモあり・質問あり・選択中・区分・月で絞る。記事ごとにメモ、ファクトの追加、「この記事に質問する」（ジョブ `research-qa`。AI が元記事を開いて読み、開けなければ検索で確かめ、どちらで答えたかを印にする）。選んだ記事は PowerPoint（一覧と1記事1枚。質問と回答はノート）に出せる。
  - 論点：論点（「論点名｜問い」で問いも持てる）ごとに、要点・主張（推進／慎重／中立と根拠の記事）・反対の見方・国内の記事・時期による変化を、記事の要約だけを根拠に AI がまとめる。新しい記事が3件たまると書き直す。
  - 技術調査・業界調査・公的データ：調査レポート（RR-n、ジョブ `research-report`）。技術は技術要素 × 文書の表・文書ごとの構成要素と処理の流れ（シーケンス図）・文書どうしのつながり、業界は広がる順の業界ごとの規模・流れ・課題・事例・制度・障壁、公的データは統計の推移・制度の動き・行政手続きのデジタル化。出典と確認日を付け、検索が使えない接続では記事集と AI の知識からまとめたことを示す。
  - 更新：見出しの「すべて更新」は1つのジョブで、記事を集めて（AI の検索・RSS・指定ページ）から、論点のまとめ（新しい記事が3件以上入った論点と古い形式のまとめ）・プレーヤーの調査と最新の動き・技術調査・業界調査・公的データのレポートを作り直す。工程はジョブの画面のグラフで見られる。各タブの「更新」（記事を更新・論点を更新・プレーヤーを更新・技術調査を更新 など）はそのタブの範囲だけを作り直す（論点は全部書き直し、調査レポートはその種類のいちばん新しいものを作り直す）。
  - プレーヤー：層ごとのマップ（最後に記事に出た日で色分け、30日の件数・姿勢）。「プレーヤーを更新」で、テーマの主要なプレーヤーを Web 検索と記事集から層・役割・取り組み・姿勢・対応規格つきで調べて足す（既にいれば空の項目を埋める）。最新の動きは「更新」のたびに登場記事から書き換える。
  - ファクトDB：種類・テーマ・国内／海外・キーワードで絞り、CSV に保存。データ分析：期間・地域・区分・論点・企業・キーワードの条件が全部に効き、概要（論点のランキングと国内／海外の割合・区分・よく出る企業）、自由集計（縦横の軸・記事かファクトか・件数か割合のヒートマップ、セルを押すと記事、CSV）、推移と増減（期間ごとの表と、直近と前の期間の割合の差）、企業・プレーヤー（企業ごとの推移・論点・一緒に出る企業、関係図）、AI に分析を頼む（根拠の記事番号つきのレポート）。定期実行はしない（画面から手で更新する）。
- ステージの AI タブの「リサーチから取り込む」：ライブラリ（と論点）を選ぶと、論点のまとめとファクトを根拠にした案を AI に頼む発言として送る（②市場分析・③競合分析での利用を想定。どのステージでも使える）。AI の案にはファクト番号・記事番号が付く。
- ドキュメント：手で書く Markdown のドキュメント（DOC-n。US-01 のように ID を書くとつながる）と、取り込んだ資料（下の「資料の取り込み」）を1つのページ（`/p/{id}/docs`）に並べる。チケット・議論・決定記録・会議は廃止した（Issue・振り返りの会議・ドキュメントに一本化。API も外した）。
- AI の利用上限（429 Resource exhausted）：1分あたりの上限に当たったら、上限が戻るまで待ってやり直す（Gemini・Vertex は4秒から倍々・最大60秒・計7回、Anthropic は retry-after を読んで6回まで）。それでもだめならジョブの失敗になり、プラットフォームが知らせる。
- GitHub の接続：テナントのトークン（設定）を、コード（IDE）・自動開発・Issue の同期（押したときだけ）が使う。webhook は使わない（チケットとの自動同期は、チケットの廃止とともに外した）。
- 右上の歯車（設定）で、テナントが使う LLM の接続を決める。接続方式は Gemini API・Vertex AI（キー不要。Gemini と Claude）・Anthropic API・OpenAI 互換 API（ローカルLLM など）・スタブ。対話・レポート・画像でモデルを分けられる（画像は Gemini 系だけ）。アプリ全体の既定はプラットフォーム管理者（`PF_ADMIN_EMAILS`）が決め、各テナントの OWNER が自分のキーで上書きできる。API キーは `PF_SECRET_KEY` から作る鍵で暗号化して DB に置き、画面には末尾4文字だけを出す。Vertex AI（キー不要）はアプリの GCP の費用になるので、選べるのはプラットフォーム管理者と、管理者が全テナントに許したときだけ。テナントの OpenAI 互換 URL は https の公開アドレスだけを受け付ける（内部ネットワークへの到達を防ぐ）。
- 「コード（IDE）」では、プロダクトに GitHub リポジトリ（owner/name とブランチ）をつなぎ、Code-OSS の Web 版で読む（読み取り専用、ターミナルなし）。Code-OSS は `ide/VSCODE_VERSION` のタグからソースでビルドし（`ide/build.sh`）、Microsoft のマーケットプレイスや製品版の資産は使わない。IDE 内の拡張機能（`ide/extension`）が `pfrepo://<プロダクトID>/` のファイルシステムとして web の `/api/p/{id}/code/*` を読み、agent-api が GitHub の REST API から木と中身を取る。非公開リポジトリは `GITHUB_TOKEN`（読み取りだけの fine-grained token）が要る。
- ループ L1〜L5、トレーサビリティ画面、worker / scheduler は R2。
- `GOOGLE_API_KEY` が無ければ LLM はスタブ（必須見出しを埋めたダミー成果物）になり、全工程をそのまま通せる。

## ローカルで動かす

```bash
cp .env.example .env   # AUTH_SECRET と PF_INTERNAL_TOKEN を埋める
docker compose up -d --build
open http://localhost   # /register で登録すると、その人が個人テナントの OWNER になる
```

コンテナを使わない場合

```bash
# agent-api
cd services/agent && python -m venv .venv && . .venv/bin/activate && pip install -e ".[dev]"
DATABASE_URL=postgresql://pf@127.0.0.1:5432/pf PF_LLM=stub uvicorn pf_agent.api:app --port 8100
# web
cd apps/web && npm ci && DATABASE_URL=postgresql://pf@127.0.0.1:5432/pf AUTH_SECRET=dev npm run dev
```

## デプロイ（Cloud Run + Supabase）

web と agent-api（と IDE）を Cloud Run に置き、DB は Supabase を使う。リージョンは DB と揃える（Terraform の `region` と Variables の `GCP_REGION`。既定は東京 `asia-northeast1`）。nginx はローカル用で、Cloud Run では使わない。

```
利用者 ─HTTPS→ Cloud Run pf-web（公開） ─ID トークン→ Cloud Run pf-agent（IAM で非公開）
                      └────────────┬──────────────┘
                         Supabase Postgres（session モードの接続プール）
```

1. **Supabase**：Cloud Run と同じ地域でプロジェクトを作る。
   - Connect → **Session pooler** の接続文字列を控え、末尾に `?sslmode=require` を付ける（パスワードに記号があれば URL エンコードする）。
   - テーブルはサーバーからだけ使うので、Project Settings → Data API を無効にする。
2. **GCP**：課金を有効にしたプロジェクトで Cloud Shell を開き、土台を作って秘密値を入れる。
   ```bash
   git clone https://github.com/<owner>/<name> && cd <name>/infra/terraform/gcp
   terraform init && terraform apply -var project_id=<PROJECT_ID> -var github_repo=<owner>/<name> -var region=<REGION>
   gcloud config set project <PROJECT_ID>
   read -rs V && printf '%s' "$V" | gcloud secrets versions add DATABASE_URL --data-file=-     # 1 の接続文字列
   read -rs V && printf '%s' "$V" | gcloud secrets versions add GOOGLE_API_KEY --data-file=-   # Gemini を使うときだけ
   terraform output
   ```
   state は Cloud Shell の手元に残る（リポジトリには入れない）。
3. **GitHub**：Environment `production` を作る（必要なら Required reviewers を付ける）。Variables に `terraform output` の `GCP_PROJECT_ID`、`GCP_REGION`、`GCP_WIF_PROVIDER`、`GCP_DEPLOY_SA` を入れる。任意で次も入れる。
   - `PF_GEMINI=true`：Gemini を使う（無ければスタブ）。`PF_MODEL` で対話のモデル、`PF_IMAGE_MODEL` で画像のモデルを変えられる。
   - `PF_ALLOW_SIGNUP=false`：自分の登録が済んだら入れて、新規登録を締め切る。
   - `PF_ADMIN_EMAILS`：プラットフォーム管理者。設定画面でアプリ全体の LLM の既定と Vertex AI の利用を決められる人のメールアドレス（複数は `;` 区切り）。
4. Actions → `deploy` → Run workflow。以後は main への push で `ci` 成功後に自動で更新される。web の URL はジョブのサマリーに出る。

5. **IDE（任意）**：Actions → `ide` → Run workflow（Code-OSS のビルドに30〜60分）。終わると web に IDE の URL（`IDE_ORIGIN`）が入る。非公開リポジトリを読むときは、読み取りだけの fine-grained token を `gcloud secrets versions add GITHUB_TOKEN` で入れ、Variables に `PF_GITHUB_TOKEN=true` を入れてから `deploy` を実行する。

Supabase の session モードは同時接続数に上限があるので、Cloud Run は各サービス最大1台、DB の接続は各2本（`PF_DB_POOL_SIZE`）にしている。
